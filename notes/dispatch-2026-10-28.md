**Title:** Decoration placement from the terrain tile — seeded, worker-parity, bank-aware (#487 D, unblocks #522 C)

**Context / motivation.** #487 made the canyon one geometry source: `src/terrain/terrainTile.ts` is the canyon floor, tube fold and wall shell as a tile of planes, read on both threads, and since PR #525 (ABI 16) it is TypeScript-only — the C++ twin is gone, and `terrainParity.test.ts` requires the sim-worker build to equal the main-thread build exactly. Meshes, hulls and the SWE bed already come from the tile. **Decoration placement does not.** `src/components/TrackSegment/TrackSegmentDecorations.tsx` and `trackSegmentPropLayouts.ts` still place rocks, trees, props and set-pieces from the CatmullRom centreline plus per-type lateral offsets and a guessed height, which is why props float at the bank, sink into the tube fold, and why "placement from the tile" was deferred by #503's PR ("one host per PR") and then left unowned when #503 closed. #522 Phase C (river stones "on risky lines": inside the vortex radius, the top of a wall-ride, the far side of a trestle gap) wants exactly this sampler and says it will ship with segment-frame placement if this is not on `main`. Active focus areas touched: procedural environment decoration, track treadmill.

**Proposed approach (first pass, Noah to expand).**
1. A pure placement module, `src/terrain/placement.ts` (three-free, like `segmentMeshBuild.ts`): given a `TerrainTile`, a segment frame, a per-type layout spec and a segment seed, return typed arrays of `(position, normal, yaw, scale, typeIndex)`. Height and normal come from sampling the tile's planes at `(s, lateral)`; "bank", "rim", "floor", "wall" are bands in the tile's own profile, not absolute Y (CLAUDE.md rule).
2. Seed with `createRng(hash(mapId, segmentId, 'placement'))` from `src/math/random.ts` — the one PRNG. Two builds of the same segment on the two threads must be byte-identical; add `placementParity.test.ts` beside `terrainParity.test.ts`.
3. `TrackSegmentDecorations.tsx` consumes the arrays into the existing `InstancedMesh`es and `InstancedRigidBodies`; no per-frame work, no new Rapier body per prop. Keep the `DecorationPlacement[]` authored path (seg-14 slab, seg-22 columns) as overrides that are snapped to the tile, not bypassed.
4. Optional second step: the sim worker's `BUILD_TILE` reply already carries the segment's mesh buffers; carry the placement arrays in the same message so a treadmill append does no placement work on the main thread. (This touches `src/sim/simWorkerCore.ts` / `simWorkerProtocol.ts`; keep it a separate commit so it can be dropped if it collides.)
5. Expose the band sampler (`sampleBand(tile, s, lateral) -> 'floor' | 'bank' | 'wall' | 'rim'`) as the hook #522 C will use for risky-line tags.

**Acceptance criteria (rough).**
- A placement parity test: worker build == main-thread build, byte-identical, for the five authored maps' first 12 segments.
- Determinism: the same `(mapId, segmentId)` gives the same arrays across two runs and across `?simWorker=0` vs default. `test:input-smoke` and `test:replay-smoke` splits and SWE checksums unchanged (decorations do not touch the SWE).
