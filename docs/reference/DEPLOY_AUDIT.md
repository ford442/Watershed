## 2. Packaging truth

`python3 deploy.py --dry-run`, run with `DEPLOY_TOKEN` unset (as required — never exported it):

```
Checking remote file sizes...
  ! sizes HTTP 403; uploading all files
  + <all 52 files>
Archive size: 8998.8 KB
Dry run: ... Stopping before network upload.
```

**Finding: in this run, the dry-run manifest is identical to the build manifest — trivially, and
for a reason worth stating plainly.** `fetch_remote_sizes()` (`deploy.py:51-71`) sends
`X-Deploy-Token` only `if token:` (line 57-58); with no token set it still makes the GET, gets back
**HTTP 403**, hits the `except`-free `if response.status_code == 200` branch's `else`
(`deploy.py:68`), prints `! sizes HTTP 403; uploading all files`, and returns `{}`. An empty
`skip_sizes` dict means `build_zip()`'s `(skip_sizes or {}).get(rel_s) == local_size` (line 88) is
never true, so every file is written to the zip. **The dry-run's fidelity to the real
(authenticated) upload behavior depends on whether the sizes endpoint is reachable and authorized
at the moment `--dry-run` is invoked** — an unauthenticated or network-failing dry run always
reports "upload everything" and tells you nothing about what the size-skip would actually skip.
That is a gap in the tool, not a bug in this run.

**Reading `build_zip()` (`deploy.py:74-93`) and `fetch_remote_sizes()` (`deploy.py:51-71`)
line-by-line, the skip mechanism is:**
- Keyed on **remote byte-size equality only** — no hash, no mtime, no ETag comparison
  (`deploy.py:88`: `if (skip_sizes or {}).get(rel_s) == local_size`).
- **Never deletes** anything remote — `build_zip` only ever adds files to the outgoing zip; there
  is no code path anywhere in `deploy.py` that removes a remote path. Confirmed by reading the
  whole file (206 lines): the only remote-affecting calls are the one `GET .../sizes` and the one
  `POST .../bundle`.
- The upload itself is **not atomic in a way this script can see**: `deploy_bundle()` sends the
  whole zip as one POST (`deploy.py:138-144`), but the server-side extraction is a separate system
  (`storage.noahcohn.com`, not in this repo) whose own docstring says it "pushes all files over one
  persistent SFTP connection" — i.e., many small remote writes behind one HTTP response, not one
  transaction. This script has no way to observe or protect against that push dying partway; see
  §5(a) item 2.

**Which classes of file can be skipped incorrectly (with a valid token this time)?** Since I can't
get a 200 from the sizes endpoint without `DEPLOY_TOKEN`, I reconstructed the equivalent
comparison directly: I fetched live byte sizes for every path in the local build manifest (§3) and
diffed them against local sizes. This is a size-for-size stand-in for what `fetch_remote_sizes()`
+ `build_zip()`'s skip check would do with a working token, and it reproduces the mechanism exactly
because the skip predicate is *only* `local_size == remote_size`:

| Path class | Local vs. live size | Would size-skip? |
|---|---|---|
| All 15 hashed `assets/*` files | Live path 404s (hash differs every build unless content is byte-identical) | **No** — a changed hash is a new remote path, `skip_sizes.get()` returns `None`, never equal, always uploads. This part of the mechanism is actually safe by construction. |
| `index.html` | Local 718 B; live serves 1438 B (UTF-16, see §3) but that's the *post-storage* size, not necessarily what the sizes API reports pre-conversion | **Unknown / can't measure** — the sizes API lives on the VPS, out of this repo's scope, and is unreachable without a token. But see §5(a) item 1: the file's *byte length is highly likely to be size-invariant across builds* because the only thing that changes in it is a fixed 8-char hash substring per reference, so any given local build has a real chance of coincidentally matching whatever length the remote already reports, independent of whether the hashes inside actually changed. |
| `watershed_native.js` | Local 27029 B; live 26999 B | **No** — sizes differ by 30 bytes, would upload |
| `watershed_native.wasm` | Local 33840 B; live 33817 B | **No** — sizes differ by 23 bytes, would upload |
| 6 `Rock031_*` textures, `collision.wav`, 4 `levels/*`, `rapier.wasm`, `shaders/heightmap_flow.wgsl`, 23 `sounds/*.mp3` (36 files total) | All byte-identical, local == live | **Yes** — all 36 would be skipped, correctly (their content hasn't changed) |

So: **the only files whose skip-by-size check is a real correctness risk are the unhashed ones
whose content changes but whose byte length doesn't move enough to differ from whatever's already
remote — and `index.html` is the one file in that class that also determines which hashed bundle
the browser loads.** §4 and §5(a) show this isn't hypothetical; it already happened once, and its
evidence is still sitting on the server.

## 5. Findings

### (a) Every way this pipeline can serve an incoherent build, ranked by likelihood

1. **Highest likelihood, already observed in the wild: an unhashed file's byte length
   coincidentally matches what's already remote, so a real content change is silently skipped.**
   Code path: `deploy.py:88` (`if (skip_sizes or {}).get(rel_s) == local_size: ... continue`) —
   size equality is the *entire* correctness check, for *every* unhashed file, forever. `index.html`
   is uniquely dangerous in this class because (i) it is unhashed, so it's subject to this check at
   all (unlike everything in `assets/`), and (ii) its only variable content — five 8-character
   Rollup hashes embedded in fixed-width `src=`/`href=` attributes — means its total byte count is
   very likely to stay constant across builds even when the hashes (and thus which bundle the
   browser loads) change completely. §3's `index-DpiTsYx-.css` orphan is measured, direct evidence
   that *some* class of file got a fresh upload on 31 Aug while `index.html` did not; that
   `index.html`'s byte-length-is-usually-invariant property is the mechanism that explains it is
   inference (I can't reach the VPS-side sizes endpoint without the token to confirm what it
   reported that day), but it is the only mechanism in this file that fits every observed fact:
   new-hash CSS/JS landed (size differed from remote → not skipped), `watershed_native.{js,wasm}`
   partially landed (size differed enough for the `.wasm` half only → not skipped for wasm, skipped
   or not-attempted for js — see finding 2), and `index.html` alone stayed byte-for-byte the old
   version.
2. **Second: the same "unhashed file, size-only check" hole, applied to `watershed_native.js` vs.
   `.wasm` as a pair, silently splits a two-file atomic unit.** Same code path
   (`deploy.py:74-93`). The glue (`.js`) and binary (`.wasm`) must come from the exact same `emcc`
   invocation — `emscripten/build.sh:66-67` says so explicitly ("Mixing 3.1.x glue with 6.x wasm...
   throws at `__embind_register_value_object_field`"). Nothing in `deploy.py` treats them as a
   pair; each is size-checked independently. On 31 Aug the `.wasm` half's byte size moved enough to
   upload; the `.js` half's did not (26999 stayed 26999, live-confirmed) — whether because its size
   genuinely didn't change, or changed by a coincidentally-matching amount, either way the two are
   now provably out of sync in production (§4). This is a structural property of the size-check
   design, not a one-off mistake: any future deploy that changes one half of the pair by a byte
   count that happens to equal the current remote size (or that changes only one half at all) will
   reproduce it.
3. **Third, lower confidence (inference, not measured): the server-side push is not a single
   transaction.** `deploy.py`'s own module docstring (lines 12-14) describes the far side as
   pushing files "over one persistent SFTP connection" — i.e., the atomicity guarantee, if any,
   lives entirely in a service outside this repo that I have no visibility into. If that push can
   die partway (network blip, disk-full on the VPS, request timeout on a multi-MB bundle), the zip
   is applied file-by-file rather than as a unit, and a partial application is indistinguishable
   from the front-end's perspective — `deploy_bundle()` only checks the HTTP response's top-level
   `failed` list (`deploy.py:151-156`), not a per-file confirmation against what was actually
   asked for. I found no direct evidence this happened for the 31-Aug event specifically (finding 1
   fully explains it without needing this), but the code has no defense against it either way, so
   it stays on the list as a live risk for any future deploy, ranked below the two above because
   there's no measured instance of it.
4. **Withdrawn (2026-09-16). There is no re-encoder.** This item originally claimed that
   something between `vite build` and Apache transcoded `index.html` to UTF-16LE. That is
   false. Re-verified with `curl -I` on 2026-09-16:

   | URL | last-modified | content-length | etag | content-type |
   |---|---|---|---|---|
   | `https://test.1ink.us/watershed/` | Fri, 14 Aug 2026 **12:21:30** | **1438** | `"59e-65900dc4a04cd"` | `text/html; charset=utf-16` |
   | `https://test.1ink.us/watershed/index.html` | Fri, 14 Aug 2026 **12:21:58** | **718** | `"2ce-65900ddf3c889"` | `text/html` |

   Two `last-modified` values prove two files on disk. One file cannot have two mtimes, and an
   Apache output filter does not rewrite `Last-Modified`. The bodies are semantically identical
   HTML (same `<title>WATERSHED</title>`, same five 08-14 asset hashes) — one stored UTF-8, one
   stored UTF-16LE with a `ff fe` BOM. Apache `DirectoryIndex` resolves the **directory URL** to
   the UTF-16 file. `deploy.py` writes only `index.html`. A perfect upload therefore changes
   nothing a browser at `/watershed/` sees: it keeps loading the 1438-byte shadow, which names
   `assets/index-8Gl23hpQ.js`, and because the upload never deletes remote files that August
   bundle still returns 200.

   This is **Mechanism 1** and it outranks the size-skip (Mechanism 2, findings 1–2). Guessed
   DirectoryIndex names (`index.htm`, `default.htm`, `default.html`, `Index.html`) all 404; the
   shadow's on-disk name is the 1438-byte root HTML file in `GET /api/deploy/watershed/sizes`
   (`python3 deploy.py --list-remote`). `verification/verify_deploy.mjs` fetches the directory
   URL, not `index.html`. Nothing re-encodes anything.
5. **Fifth, lowest severity: the dry run itself doesn't mean what it looks like it means without a
   working token.** (§2.) Not a way to *serve* an incoherent build, but a way to be falsely
   reassured about one before deploying — a `--dry-run` in an environment where the sizes endpoint
   is unreachable reports "upload everything," which looks like a conservative worst-case but
   actually tells you nothing about which files a *real* run would (or wouldn't) skip.

### (b) What is currently orphaned on the server (measured)

- **179 files in `/watershed/assets/`, ~274 MB, dated 2026-02-06 through 2026-08-30.** Every
  content-hashed bundle ever uploaded and never superseded by the exact same filename is still
  there; nothing in `deploy.py` deletes. Includes at least one bundle (`index-DpiTsYx-.css`) that
  is `HEAD`'s current output, uploaded 9 days ago, and never linked to.
- **4 files in `/watershed/shaders/`** (`sky.wgsl`, `terrain.wgsl`, `tree.wgsl`, `water.wgsl`,
  all dated 2026-06-28) that the current codebase no longer generates at all — confirmed against
  both `public/shaders/` and this session's `build/shaders/` (both contain only
  `heightmap_flow.wgsl`). These are dead weight from a shader-architecture change with no
  corresponding cleanup.
- **`levels/`, `sounds/`, and the 6 `Rock031_*` root textures have no orphans** — every file present
  matches something the current build still produces.

### (c) The minimum change that would make "which commit is live?" answerable in one command

Given everything above, the smallest change that actually closes the gap is **not** a bigger
rewrite of the upload mechanism — it's making the one file that already determines the whole
bundle's identity (`index.html`) *provably* carry a build identity, and then giving whoever is
asking a single thing to fetch and compare:

1. Add one `vite.config.ts` `define` (e.g. `__BUILD_ID__`, a short git SHA or content hash of the
   full manifest) and stamp it into `index.html` as an HTML comment or a `<meta>` tag — since it's
   part of the templated HTML content, it participates in the existing byte-length-changes-on-real-
   change property that already protects every other Vite-hashed file, which *also* incidentally
   fixes finding (a)(1): a build-id `<meta>` tag whose value changes every build means `index.html`
   can no longer coincidentally match a stale remote byte count.
2. Serve that same identifier at one fixed, unhashed, well-known path (e.g. `/watershed/BUILD_ID`
   or a `X-Build-Id` response header on `index.html` if the VPS-side server can be configured to add
   one) so "what's live" is `curl https://test.1ink.us/watershed/BUILD_ID` — one command, no page
   execution, no directory-listing archaeology like this audit had to do.
3. That alone would have made every finding in this report visible from a single `diff` between
   `git rev-parse HEAD` and that one fetched value, instead of a 52-file manifest, a directory-listing
   sweep, and a byte-for-byte CSS comparison.

This is a recommendation, not a patch — no code was changed as part of this audit, per the task's
scope lock on `deploy.py`, `build_and_patch.py`, and `verification/`.
